## 一、测试环境与方法

| 项 | 值 |
|---|---|
| CPU | AMD Ryzen 7 8745HS（Zen 4，8C/16T，**单线程运行**） |
| 编译器 | GCC 16.2.0（MinGW-w64） |
| 编译选项 | `-Wall -O3`，**不加任何 `-m` 开关** |
| 计时方式 | `GetTickCount()` / `clock_gettime(CLOCK_MONOTONIC)`，毫秒 |
| 取数方式 | 连续 `-n=10` 帧，输出**总毫秒数** |

### 为什么是 10 帧取总时间

1. **摊平首帧冷启动**：第一次 `net_forward` 要把权重从内存拉进 cache，
   单独计时会把这次冷读算进去，结论不稳定；
2. **避免单帧计时分辨率问题**：Windows 的 `GetTickCount()` 分辨率约 15.6 ms，
   yolo-fastest 的 avx2 单帧只有 12 ms 左右 —— 单帧读数毫无意义；
3. **总时间可以直接除**：`总 ms / 10` 即平均单帧耗时，精度足够做 2~8 倍的对比。

### 测量注意事项

- 结果对**频率变化**敏感。笔记本上跑请接电源、避免省电模式；同一批对比务必连续测完。
- `orig` 在 mbv2 上单帧要 789 ms，10 帧接近 8 秒 —— 对比时要有耐心，别以为卡死了。
- 绝对值在不同时刻可差 **5~10%**（热降频、后台负载）。复测时若整体偏移，看**加速比**而不是绝对值：
  同一次测量内三套实现的相对关系稳定得多。实测过一次整体偏慢约 6% 的情况
  （yolo-fastest `orig` 1109 / `opt` 469 / `avx2` 140 ms，加速比 2.36× / 7.92×），
  与上表的结论一致。

## 二、端到端结果

10 帧总耗时，单位 ms：

| 模型 | 输入 | `orig` | `opt` | `avx2` | opt 加速 | avx2 加速 |
|---|---|---|---|---|---|---|
| yolo-fastest-1.1 | 320×320×3 | 1046 | 453 | **125** | 2.31× | **8.37×** |
| mbv2_yolov3_face | 416×416×3 | 7891 | 2875 | **1203** | 2.74× | **6.56×** |

平均单帧：

| 模型 | `orig` | `opt` | `avx2` |
|---|---|---|---|
| yolo-fastest-1.1 | 104.6 ms | 45.3 ms | **12.5 ms** |
| mbv2_yolov3_face | 789.1 ms | 287.5 ms | **120.3 ms** |

**观察**：

- `opt` 的两项主要收益（BN 折叠 + 几何特化）对两个模型都有效，但 mbv2 更高（2.74× vs 2.31×）——
  因为 mbv2 的 1×1 与 depthwise 层占比更高，几何特化的收益更大。
- `avx2` 在 yolo-fastest 上更快（8.37× vs 6.56×）。原因是 mbv2 有小空间尺寸 + 大通道数的层
  （如 `13×13×320/960`），向量化的尾部与寄存器压力更明显。
- 8 倍的端到端加速是**标的量级**：在这个算术强度下，标量单链实现本来就有 4~8 倍的空间。

## 三、内核耗时占比

在 `opt` 路径下按内核类型拆分（三套实现在同一层的分流条件相同，占比结构相近）：

| 模型 | depthwise | 1×1 | 通用 im2col | 其它层 |
|---|---|---|---|---|
| yolo-fastest-1.1 | 36.7 % | **59.0 %** | 2.5 % | 1.8 % |
| mbv2_yolov3_face | 13.7 % | **77.8 %** | 7.3 % | 1.2 % |

```
 yolo-fastest-1.1                    mbv2_yolov3_face
 ┌────────────────────────────┐      ┌────────────────────────────┐
 │ 1x1               59.0%    │      │ 1x1               77.8%    │
 ├──────────────────────┬─────┤      ├──────────────────────┬─────┤
 │ depthwise   36.7%    │2.5% │      │ depthwise  13.7%     │7.3% │
 └──────────────────────┴─────┘      └──────────────────────┴─────┘
   ↑                                   ↑
   1x1 已是最大项，                     1x1 压倒性主导，
   但仍要先把 depthwise 做好            depthwise 其次
```

**结论：1×1 卷积是绝对瓶颈。** 这也解释了为什么 `conv_1x1_avx2` 的"4 输出通道共享一次 load"
是单点收益最大的改动 —— 它作用在 59%~78% 的运行时上。

> "其它层" 指 maxpool / upsample / shortcut / route / yolo / NMS。
> 它们在两个模型里都不到 2%，因此**不值得为它们写专用内核**。

## 四、加速比从哪里来

### 4.1 `orig` → `opt`（2.3~2.7×）

四项改动，按重要性排序：

| 改动 | 主要作用的层 | 说明 |
|---|---|---|
| **BN 折叠** | 所有 BN 层（几乎全部） | 去掉每输出元素一次的 `fast_inverse_sqrt`（≈10 条指令 + 一次牛顿迭代）。对 `ftotal` 小的 layer（如 depthwise 的 9）收益最大 —— 归一化的成本快赶上点积本身 |
| **几何特化** | 1×1 与 depthwise 层 | 跳过 im2col，直接做通道点积 / 直卷积。省下的是**纯拷贝**开销 |
| **一次性 im2col** | 通用 3×3 层 | 每个滤波器复用同一份 `col`，拷贝量被 `n` 摊薄 |
| **`dot4` + 按行写** | 通用层 | 打破浮点加法串行依赖；写指针连续 |

### 4.2 `opt` → `avx2`（2.4~3.0×，取决于模型）

| 内核 | 手段 | 实测加速（相对 opt） |
|---|---|---|
| `conv_1x1_avx2` | 8 float/向量 + 4 输出通道共享一次 load | **1.5~2.3×** |
| `conv_depthwise_s2_avx2` | `dw_gather2` 3 指令取 8 个跨步元素 | **1.7×** |
| `conv_depthwise_avx2` | 权重常驻寄存器 + 9 条 FMA | ~2× |
| `dot4_avx2` | 8 路 + 双累加器 + FMA | 通用层受益，占比小 |

整体 `opt → avx2` 是 3.6×（yolo-fastest：453→125）和 2.4×（mbv2：2875→1203）。
**比单个内核的加速比更高**，原因：

1. 三套内核同时向量化，收益叠加；
2. AVX2 版还能用 FMA（一次舍入而非两次），减少指令数；
3. 向量化后内存访问次数不变但**指令数**大幅下降，前端瓶颈缓解。

### 4.3 为什么理论上限没吃到

1×1 卷积理论上限大约是 8×（向量宽度）。实测 1.5~2.3×，差距来自：

| 限制 | 说明 |
|---|---|
| **load 端口** | 每个输入元素被 4 个输出通道复用，但每 4 次 FMA 仍需 1 次 256 位 load；Zen 4 的 load 端口能支持，但加上权重广播就紧张 |
| **权重广播** | 每个 `c` 迭代要 4 次 `set1`（`vbroadcastss`），占指令槽 |
| **内存带宽** | mbv2 最深的层输入 960×13×13 ≈ 650 KB，超出 L2 单核配额（Zen 4 每核 1 MB，但还有其它数据竞争） |
| **尾部** | 宽度 13 的层（`13×13`）只有 8 个像素能走向量路径，5 个走标量尾部 |

## 五、编译器选项实测

在**全局**加 `-m` 选项时，mbv2 416×416 的 10 帧总耗时：

| 编译选项 | 耗时 | 备注 |
|---|---|---|
| `-O3` + 文件级 `#pragma GCC target("avx2,fma")` | — | **最终采用方案**，与 `-Wall -O3` 一致 |
| `-O3 -mavx2 -mfma`（全局） | **2547 ms** | 全局实验中的最快值 |
| `-O3 -march=native`（全局） | 2875 ms | **比显式 `-mavx2 -mfma` 更慢** |

### 结论

1. **不用 `-march=native`**。Zen 4 上它并不更快，且会把产物绑定到构建机指令集，
   在老 CPU 上直接 `SIGILL` —— 连运行期降级的机会都没有。
2. **不用任何全局 `-m` 开关**。AVX2 指令只出现在 `kernels/avx2/kernel_conv_avx2.c`，
   由文件级 `#pragma GCC target` 引入。其它文件的代码生成完全不受影响。
3. 构建脚本保持 `-Wall -O3`，这样同一份产物可以在任意 x86-64 上加载，
   由 `kernel_avx2_supported()` 决定实际跑哪条路径。

> 上表是"全局 `-march`"实验的数据，用于说明**为什么不用全局选项**，
> 不代表最终代码的编译方式。最终产物不含任何全局 `-m` 开关。

## 六、已排除的优化

完整记录（含原因与数据）在 [kernels.md 第六节](kernels.md#六试过但无效的优化)。这里只列结论：

| 尝试 | 结果 | 决定 |
|---|---|---|
| 1×1 内核改 8 路输出通道分块 | `13×13×960→320` 退化到 **0.77×** | 保持 4 路 |
| depthwise 激活函数外提 | `-O3` 下 **0.67~0.75×** | 保持内层 `VACT` |
| 全局 `-march=native` | 比 `-mavx2 -mfma` 慢，且破坏可移植性 | 用文件级 pragma |
| 把 `orig` 的 rsqrt 换成精确值 | 会破坏逐位基线 | 用 `KERNEL_ORIG_EXACT_RSQRT` 开关替代 |

## 七、后续优化方向与优先级

按"收益 / 成本"排序。**下列预期均为估计，未实测**，采纳前请先做基准验证。

### P0：多线程（预期 3~6×，成本中）

这是剩下唯一能带来数量级提升的方向。可行性高的切入点：

| 方案 | 并行粒度 | 优点 | 难点 |
|---|---|---|---|
| 1×1 内核按输出通道切 | `i` 循环（输出通道） | 输出不重叠，无同步 | 输入被多线程共享读，需保证只读 |
| 1×1 内核按行切 | `y` 循环 | 各线程读同一批输入平面，cache 复用最好 | 行数少的层（13 行）分不均 |
| 通用 im2col 按组切 | `groups` 循环 | 天然独立 | depthwise 组数 = 通道数，粒度够细 |
| depthwise 按通道切 | `c` 循环 | 完全独立，无假共享 | — |

**收益估计**：8 核上 1×1 占 78% 的模型，理论 4~5×；实际上受内存带宽限制，
mbv2 最深层可能就是带宽瓶颈，估计 3~4×。

**成本**：需要引入线程池（Windows `CreateThread` / POSIX `pthread`），
`build-*.sh` 加 `-lpthread`；arena 是共享的但各线程写不同区域，**不会假共享**
（因为切片是整平面级别，远大于 64 字节）。

### P1：1×1 内核的二维分块（预期 +10~25%，成本低）

当前内层是 `c → y → x`，对每个 `c` 遍历整个输出平面（`ow*oh`）。
如果输出平面大于 L1/L2，输入平面在每个 `c` 上被完整扫一遍，第二次扫就 cache miss。

改成 `c（外层）` + `(y 分块)`：

```
for i in 0..N step 4:
    for yb in 0..oh step 8:            # 输出行分块
        for c in 0..C:
            for y in yb .. yb+8:       # 8 行在 cache 里
                for x: fmadd...
```

好处：8 行 × `ow` 个 float 的输入片段在 L1 里，可以跨多个 `c` 复用。
代价：需要为每个行块重写累加器（`a0..a3` 变成 `8 × 4` 个向量，寄存器不够）——
所以实际要改成"4 个输出通道 × 4 行"之类的组合，收益要实测。

> 这一项的可行性需要先验证：mbv2 的 1×1 层大多数宽高 ≤ 52，
> 输入平面 52×52×C 在 C ≤ 128 时约 1.4 MB，已经超出 L2。**值得试**。

### P1：权重打包成 SoA（预期 +5~15%，成本低）

当前 1×1 内核每次 `c` 迭代做 4 次 `_mm256_set1_ps(W[i+k][c])`，
即 4 条 `vbroadcastss`。如果把权重重排成"每 4 个输出通道一组、组内按 `c` 连续"的布局，
可以一次 `loadu` 取 4 个权重再用 `permute` 分配 —— 省下 load 但不能省 permute，
**需要实测才能确定净收益**。

代价：需要在 `net_bn_fold` 之后额外做一次权重重排（约 n×C 次写，一次性成本可忽略），
并且让 `data2` 的布局与 `orig` 不再兼容（要额外维护一份布局）。

### P2：通用 depthwise 的向量化（预期小，成本低）

目前非 3×3 的 depthwise 落到通用 im2col 路径。实测两个模型都没有这种层
（`yolo-fastest` 与 `mbv2` 的 depthwise 都是 3×3），所以**收益为 0**。
只有在换模型时才值得做。

### P2：半精度 / 量化（预期 2~3×，成本极高）

把权重与激活降到 `fp16` 或 `int8`：

- `fp16`：AVX2 没有原生 `fp16` FMA（需要 `F16C` 转换 + `fp32` 计算），
  实际只能省内存带宽，计算量不变。对内存受限的层有效。
- `int8`：需要 `VNNI`（AVX-512 或 Zen 4 的 AVX-VNNI），且要重做量化校准、
  激活的定点近似 —— 是"另起一个引擎"的量级。

**结论**：如果目标是"能跑就行"，停在当前状态；如果要做产品级推理，直接用
ONNX Runtime / ncnn / MNN 走量化路径，不要自己重写。

### P3：算子融合（预期 +5~10%，成本高）

典型的可融合模式：

| 模式 | 融合后 | 收益 |
|---|---|---|
| `conv → BN` | 已做（BN 折叠） | ✅ 已完成 |
| `conv → shortcut` | 输出直接累加到目标 | 省一次整平面读写 |
| `depthwise → 1×1` | 中间结果留在 cache | 省一次整平面读写 |

省的是**内存带宽**而不是计算量。对小特征图收益小，对 `52×52` 以上的层可能有感。

### 不值得做的方向

| 方向 | 为什么不值得 |
|---|---|
| 给 maxpool / upsample / route 写专用内核 | 合计 < 2% 的运行时 |
| 为 `orig` 做任何性能优化 | 它的职责是"逐位基线"，不是性能 |
| 手写 AVX-512 | Zen 4 的 AVX-512 是双泵 256 位，收益约为 0；且大幅缩小可运行硬件范围 |
| 引入 BLAS / OpenMP | 与"零依赖、可读实现"的项目定位冲突 |

## 八、为什么没做多线程

当前实现是**单线程**，这是有意的：

1. **项目定位**是"把推理引擎拆开看清楚"。多线程会把注意力从"数据布局与内核算法"
   转移到同步与调度上，而后者对理解 CNN 推理没有帮助；
2. **可移植性**：加了线程就必须处理 `pthread` / `CreateThread` 的平台差异；
3. **arena 是共享的**：虽然各线程写不同平面不会假共享，但要保证这一点需要
   精心设计切片边界（按整平面切，而不是按 cache 行切），这属于另一层复杂度；
4. **单线程已经足够**：mbv2 在 120 ms/帧，对笔记本 CPU 来说已经到"能用"的边缘。

如果你要加多线程，第七节 P0 给了切入点。

## 九、如何复现

### 9.1 端到端耗时

```bash
# 编译（Linux / Windows-MinGW 各用对应脚本）
sh build-linux.sh
# 或
sh build-win.sh

# 三套实现各跑 10 帧
./test                       # orig
./test -opt                  # opt
./test -avx2                 # avx2
```

输出末行的 `xxxms` 就是 10 帧总耗时。

### 9.2 确认实际跑的是哪条路径

```bash
./test -avx2
# conv kernel : avx2 (requested avx2)      ← 实际 avx2
# conv kernel : opt (requested avx2)       ← 发生了降级（CPU 不支持）
```

### 9.3 逐层 / 逐内核耗时剖析

仓库里**没有**内置 profiling harness（开发期的临时脚本未入库）。
要复现第三节的占比数据，有两种做法：

**做法 A：在派发层加计时（最快）**

```c
/* kernels/common/kernel_common.c，仅用于剖析，不要提交 */
#include <time.h>
static double g_time[3] = {0,0,0};
static long   g_cnt [3] = {0,0,0};

void kernel_conv_forward(NET *net, LAYER *ilayer, LAYER *olayer)
{
    int kind = /* 复制 opt 里的 is_dw / is_1x1 判定 */;
    struct timespec a, b;
    clock_gettime(CLOCK_MONOTONIC, &a);
    ... 原有派发 ...
    clock_gettime(CLOCK_MONOTONIC, &b);
    g_time[kind] += (b.tv_sec-a.tv_sec)*1e3 + (b.tv_nsec-a.tv_nsec)*1e-6;
    g_cnt [kind] ++;
}
/* 在 main 返回前打印 g_time / g_cnt */
```

> 注意：计时函数本身的开销（两次 `clock_gettime` ≈ 40 ns）对细微层会有偏差，
> 只适合看**量级**，不要用它比较 1 ms 以下的层。

**做法 B：逐层累加（最准，但要改签名）**

在 `net_forward` 的层循环里对 `i` 计时，把结果累加到 `net` 上的统计数组。
缺点是侵入性大、要改结构体。

### 9.4 跨实现一致性（顺带验证没改坏结果）

```bash
gcc -O3 test_consistency.c bmpfile.c parser.c layer_conv.c layer_pool.c \
    layer_misc.c layer_yolo.c nms.c net.c \
    kernels/common/kernel_shared.c kernels/common/kernel_common.c \
    kernels/orig/kernel_conv_orig.c kernels/opt/kernel_conv_opt.c \
    kernels/avx2/kernel_conv_avx2.c -o t_cons -lm

./t_cons test.bmp yolo-fastest-1.1.cfg yolo-fastest-1.1.weights
```

性能优化后务必跑一次 —— 见 [testing.md](testing.md)。
